# ECO — rev3: firmware update over USB-C with the STM32 ROM USB DFU bootloader

Status: **schematic reviewed**. One required correction (PB6 → PC6), plus several
out-of-scope edits to confirm. Firmware port is fully specified in §6 and can be
applied from this document alone.

Supersedes the UART/FT234XD flashing scheme in
[`ECO-rev3-boot0.md`](ECO-rev3-boot0.md). That document's BOOT0 analysis still
holds; its `~RTS`/N-FET strap and the I²C re-pin table are replaced by §4 and §2
here.

---

## 1. Decision

Flash over USB-C using the **STM32G474's built-in ROM USB DFU bootloader** on
**PA11 (`USB_DM`) / PA12 (`USB_DP`)**.

- No bridge chip, no custom bootloader, no host script.
- `dfu-util` or STM32CubeProgrammer work out of the box.
- The **FT234XD (U12) is removed**, along with the whole USART3 service-mode path.
- Entry is a hardware strap: **BOOT0 (PB8) button to +3V3**, `NRST` button.
- SWD (J4) remains the always-works fallback.
- Two isolated I²C buses are preserved: **PD bus = I2C2 (PC4/PA8)**,
  **OLED + EEPROM bus = I2C4 (PC6/PB7)**.
- The quadrature encoder moves to **TIM3 QEI on PB4/PB5** — same X4 hardware
  decoding, same firmware driver, different timer.

Why PA11/PA12 are forced: on the STM32G474 `USB_DM`/`USB_DP` exist on **no other
pins**. PA11 was the converter-disable output and PA12 was encoder B, so both
had to move.

Every row was checked against the STM32G474CEU symbol in `MCU.kicad_sch` **and**
the HAL pin-trait table generated by `embassy-stm32` for `stm32g474ce`, and then

| `USB_DP` | — | **PA12** | USB device, AF0 | `usb::DpPin, USB, PA12` |

**TIM3 is QEI-capable.** `embassy_stm32::timer::qei::Qei` requires
`T: GeneralInstance4Channel`; TIM3 is a general-purpose 16-bit 4-channel timer,
exactly like the TIM4 it replaces. Proof by compilation in §10.

**Net names do not change** — only the MCU pins. `I2C0_SCL`/`I2C0_SDA` keep the
PD bus (`U9` INA228, `U4` TPS26750, `R31`/`R32`); `I2CC_SCL_MCU`/`I2CC_SDA_MCU`
keep the OLED socket (`J5`) and the EEPROM jumpers (`JP8`/`JP9`, `R88`/`R89`).
That means the existing pull-ups travel with their buses automatically.

### Spare pins after rev3

`PA2`, `PA5`, `PA10`, `PB2`, `PB6`, `PC10`, `PC11` — plus `PB3` if the
`SWITCH_EN_MANUAL` removal in §9.2 is kept.

## 3. ⚠️ Required correction: PB6 is not I2C-capable

**The schematic currently routes `/MCU/I2CC_SCL_MCU` to `U2` pin 44 (PB6). That
is not valid.** PB6 has **no I2C alternate function at all** on the STM32G474.

PB6's complete alternate list (from the MCU symbol): `COMP4_OUT`, `FDCAN2_TX`,
`HRTIM1_EEV4`, `HRTIM1_SCIN`, `LPTIM1_ETR`, `SAI1_FS_B`, `TIM16_CH1N`,
`TIM4_CH1`, `TIM8_BKIN2`, `TIM8_CH1`, `TIM8_ETR`, `UCPD1_CC1`, `USART1_TX`.
Nothing I²C. The HAL agrees: `I2C1` exposes only `SCL = PA13, PA15, PB8` and
`SDA = PA14, PB7, PB9` — no PB6. Compiling it produces
`error[E0277]: the trait bound 'PB6: SclPin<I2C1>' is not satisfied`.

**Fix:** move `/MCU/I2CC_SCL_MCU` from **PB6 (pin 44)** to **PC6 (pin 29)**.
PB7 stays as `/MCU/I2CC_SDA_MCU`; together they are `I2C4`. **PC6 is currently
unconnected**, so this is a one-net move with no side effects. PB6 becomes a
spare.

> Do not ship the PCB without this fix — the OLED and the MCU-side EEPROM
> flashing path would both be dead.

### 4.2 Still to do

1. **Move `/MCU/I2CC_SCL_MCU` from PB6 to PC6** (§3).
2. **BOOT0 pull-down value.** `R59` = 357 kΩ works (STM32G4 BOOT0 has no
   internal pull, and the button drives it hard to +3V3), but ST's reference
   designs use 10 k–100 k. **100 kΩ** is the safer choice for noise margin.
3. **Logic power for DFU.** The `+3V3` rail comes from the buck whose input is
   selected by `JP13`, which currently defaults to **VPP (XT90)**. With only a
   USB-C cable connected to a PC and no XT90 input, the MCU is unpowered and
   nothing enumerates. Either:
   - bridge `JP13` 2–3 (`+VBUS`), or
   - OR `VPP` and `+VBUS` into the buck input so either source powers the logic, or
   - accept that the normal input supply must be connected while flashing.
4. **Optional:** expose `PC10`/`PC11` (freed USART3) on a debug header or test
   pads. They are free, and a hardware UART is useful for bring-up even with
   USB DFU in place.
5. **Optional:** if the SBU-channel data path is disliked, add a `USBLC6-2SC6`
   and wire the connector D+/D- straight to PA11/PA12. The existing path is
   fine for full-speed (12 Mbit/s) and gives short-to-VBUS protection.

### 4.3 BOOT0 strap behaviour

| condition | BOOT0 (PB8) | result |
|---|---|---|
| power-up / reset, `SW2` not pressed | LOW via `R59` | application boots |
| `SW2` held, then reset | HIGH via `SW2` | ROM USB DFU, stays |

## 5. Option bytes

Program once per board:

- **`nSWBOOT0 = 1`** — BOOT0 is taken from the PB8 pin (otherwise the pin is
  ignored and the software `nBOOT0` bit decides).
- **`nBOOT1 = 1`** — BOOT0-high selects system memory.

`FLASH_OPTR`: **`0xFBEFF8AA` → `0xFFEFF8AA`** (bit 26 set).

Verify with STM32CubeProgrammer → Option Bytes, or by SWD. With PB8 forced high
the device must enter the loader on reset and stay there.

> The two boot-entry schemes are mutually exclusive. This ECO uses the
> **hardware strap** (`nSWBOOT0 = 1`). Do **not** also implement the
> `nBOOT0`-software entry from `ECO-rev3-boot0.md` §7 — it requires
> `nSWBOOT0 = 0`.

## 6. Firmware port

This section is self-contained: an agent with only this document and the repo
can perform the port.

### 6.1 Pin assignment to apply

```
USB_DM            = PA11
USB_DP            = PA12
BOOT0             = PB8      (hardware; nothing in firmware)
converter disable = PB1      (Output)
encoder button    = PB0      (Input, Pull::Up)
encoder A / B     = PB4 / PB5   : Qei on TIM3
PD bus            = I2C2 : SCL=PC4, SDA=PA8    DMA1_CH1 (TX), DMA1_CH2 (RX)
OLED bus          = I2C4 : SCL=PC6, SDA=PB7    DMA1_CH3 (TX), DMA1_CH4 (RX)
```

## 7. Flash procedure

1. Hold **BOOT0** (`SW2`), press and release **NRST** (`SW3`), release BOOT0.
2. The device enumerates as STM32 DFU: `0483:df11`.
3. Write:

```bash
dfu-util -a 0 -s 0x08000000:leave -D firmware.bin
# or: STM32CubeProgrammer -> USB -> Download
```

`-s 0x08000000:leave` tells the loader to start the application after the write.

**Recovery:** SWD on `J4` always works, even with a corrupt application. A bad
flash is never a brick.

## 8. Bench verification checklist

1. `FLASH_OPTR` reads back `0xFFEFF8AA`.
2. `SW2` released, power cycle → application runs (OLED up), PB8 ≈ 0 V.
3. `SW2` held + `SW3` tapped → `lsusb` shows `0483:df11`; `dfu-util -l` lists
   the device.
4. Full write of `firmware.bin` completes and the `:leave` command starts the
   application.
5. Scan I2C2: INA228 `0x40`, TPS26750 `0x21`.
6. Scan I2C4: SSD1306 `0x3C`, CAT24C512 `0x50` when `JP8`/`JP9` are bridged.
7. Encoder: turning one detent produces exactly one `EncTurn` in each
   direction (same behaviour as the TIM4 build).
8. **Converter state during DFU** — with a load attached, confirm the output
   stays parked across a BOOT0+RST entry (see §9.4).

## 9. Open items and findings outside this ECO's scope

The netlist diff against the previous revision surfaced changes that are **not
part of the USB-DFU work**. These are flagged, not judged.

### 9.1 Required before fabrication

- **PB6 → PC6** for `/MCU/I2CC_SCL_MCU` (§3). This is a hard error.

### 9.2 Power-path edits — confirm intentional

Also present in the current schematic, unrelated to flashing:

- `U7` removed (was on `/USB-PD/PP_EN2`, `/USB-PD/PP_EN3`,
  `/MCU/SWITCH_EN_MANUAL`, `+3V3_LDO`, `GND`).
- `JP14` and `R37` removed; `/MCU/SWITCH_EN_MANUAL` no longer exists.
- `U2.41` PB3 freed (was `/MCU/SWITCH_EN_MANUAL`).
- `R41` and `R91` moved from `/USB-PD/PP_EN3` to `/USB-PD/PP_EN2`.

This removes the MCU's manual switch-enable override and changes the 240 W
power-path enables. If these were deliberate, fine — but they should be a
separate, explicitly-reviewed change. `/MCU/SWITCH_EN_READ` (PB14) is still
present and still readable, so the firmware's read path is unaffected.

### 9.3 Power for enumeration

See §4.2 item 3 (`JP13`). Without it, "plug into a PC and flash" needs the
normal input supply connected too.

### 9.4 Converter state during reset

Moving the disable from PA11 to PB1 does not change the underlying hazard: the
pin floats while the ROM loader runs, and the converter's state is set by the
`R7`/`R8` divider (see the `/Converter/Conv-Disable` finding in `BENCH.md` and
the note in `src/board.rs`). PB1 floats exactly like PA11 did. Verify the
divider holds the converter **off** through a DFU session before flashing with
a load attached.
